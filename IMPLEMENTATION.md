# muro — Implementation Plan

This document turns SPEC.md (product/architecture) and DESIGN.md
(implementation decisions) into an actual build plan: repo layout, exact Go
packages and dependencies, the file/function breakdown per package, the
control API wire protocol, config schemas, build tooling, and a
dependency-ordered milestone sequence. Nothing here overrides SPEC.md or
DESIGN.md — where this plan had to make an additional call neither of those
docs made explicitly, it's flagged in §13.

## 4. Build Order (dependency-ordered phases)

Each phase only depends on packages from earlier phases — build and unit-test
in this order so nothing is blocked waiting on a package that isn't done yet.

| Phase | Package(s) | Depends on | Can be fully unit-tested without bwrap/MQTT? |
|---|---|---|---|
| 0 | repo bootstrap, `go.mod`, `Makefile` | — | n/a |
| 1 | `internal/config` | — | Yes |
| 2 | `internal/state` | `internal/config` (Sandbox uses profile-shaped fields) | Yes |
| 3 | `internal/sandbox` (`Isolator` interface + fake) | `internal/config`, `internal/state` | Yes, against a `FakeIsolator` |
| 4 | `internal/sandbox` (`bwrap.go` real implementation) | Phase 3 | No — needs `test/integration` (§10), real `bwrap` on `PATH` |
| 5 | `internal/proxy` | `internal/state` (denied-event logging) | Yes — `httptest`, a local TLS test server for SNI |
| 6 | `internal/pubsub` | `internal/config` (broker address, topic root) | Partially — topic-name builders yes; claim/LWT needs a real broker, test against `muro-broker` in CI |
| 7 | `internal/control` (protocol + server, wired to a `FakeIsolator`-backed manager) | Phases 1–6 | Yes |
| 8 | `cmd/murod` (wires config → state → sandbox → proxy → pubsub → control server) | Phase 7 | No — this is the integration point, exercised in `test/integration` |
| 9 | `internal/control/client.go` + `internal/cli` | `internal/control` (protocol types) | Yes — against a fake control server |
| 10 | `cmd/muro` | Phase 9 | n/a — thin `main.go` |
| 11 | `cmd/muro-broker` | none (just wraps `mochi-mqtt/server`) | Can build in parallel with anything above |
| 12 | `internal/sandbox/pty.go` (attach) + `control/stream.go` | Phases 4, 7 | Partially — exclusivity/detach logic yes, real pty behavior needs `test/integration` |
| 13 | `systemd/`, `scripts/install.sh` | everything built | n/a |

Phases 1, 2, 5, and the fake-backed halves of 3/7/9 have no OS-level
dependency and can be built and fully unit-tested on any machine (including
non-Linux, for iteration speed) before touching `bwrap` or a real broker at
all.

Signatures below are the plan, not final code — they exist so each package's

### `internal/config`

func ConfigDir() (string, error)   // $XDG_CONFIG_HOME/muro or ~/.config/muro
func StateDir() (string, error)    // $XDG_STATE_HOME/muro or ~/.local/state/muro
func ProfilesDir() (string, error)

// daemon.go
type DaemonConfig struct {
    ControlSocketPath string `yaml:"control_socket_path"`
    Broker            BrokerConfig `yaml:"broker"`

    Agent         string   `json:"agent"`
    Mounts        []Mount  `json:"mounts"`

    DenyURLs      []string `json:"deny_urls"`

}

func ListProfiles() ([]string, error)

### `internal/state`

```go
// sandbox.go
type SandboxState string
const (
    StateRunning SandboxState = "running"
    StateStopped SandboxState = "stopped"
    StateReloadPending SandboxState = "reload-pending"
    StateCrashed SandboxState = "crashed"
    StateRestarting SandboxState = "restarting"
    StateRestartExhausted SandboxState = "restart-exhausted"
)
type Sandbox struct {
    ID          string    // internal id, e.g. "sb_8f2a1c" — storage key only
    Name        string    // human name — the CLI-facing identifier (DESIGN §9)
    Namespace   string
    Profile     string    // profile name this was launched from
    Agent       string
    PID         int
    State       SandboxState
    StartedAt   time.Time
    Mounts      []config.Mount
    Tools       []config.Tool
    AllowURLs   []string
    RestartPolicy string
    RestartCount  int
}

// store.go
type Store struct { /* mu sync.RWMutex; sandboxes map[string]*Sandbox; deniedEvents *events.Ring */ }
func NewStore(path string) *Store
func (s *Store) Load() error              // reads state.json if present
func (s *Store) persist() error           // write-temp+rename, called after every mutation
func (s *Store) Put(sb *Sandbox) error
func (s *Store) Get(namespace, name string) (*Sandbox, bool)
func (s *Store) List(namespace string) []*Sandbox   // namespace == "" -> all
func (s *Store) Delete(namespace, name string)
func (s *Store) RecordDenied(namespace, name, host, url string)

// events.go
type Ring struct { /* fixed-capacity ring buffer */ }
func NewRing(cap int) *Ring
func (r *Ring) Push(e DeniedEvent)
func (r *Ring) Last(n int) []DeniedEvent

// reconcile.go
func Reconcile(store *Store) error   // for every "running" entry, verify PID is alive
                                       // and is actually a bwrap/sandbox process;
                                       // otherwise mark "stopped (unclean)"
```

### `internal/sandbox`

```go
// isolator.go
type LaunchSpec struct {
    Mounts []config.Mount
    Tools  []config.Tool
    Env    map[string]string
    Cmd    []string
    PTY    bool
}
type Isolator interface {
    Launch(ctx context.Context, spec LaunchSpec) (Handle, error)
    UpdateMounts(h Handle, mounts []config.Mount) (applied bool, err error) // live if possible
    Stop(h Handle) error
}
type Handle interface {
    PID() int
    Wait() (exitCode int, err error)
    Stdio() (pty *os.File, ok bool)   // ok=false if not launched with PTY:true
}

// bwrap.go
type BwrapIsolator struct{}          // implements Isolator by exec'ing `bwrap`
func NewBwrapIsolator() (*BwrapIsolator, error)  // checks `bwrap` on PATH, checks
                                                   // unprivileged userns enabled (DESIGN §8)
func (b *BwrapIsolator) buildArgs(spec LaunchSpec) []string

// mounts.go
func ResolveMounts(p *config.Profile) ([]config.Mount, error)  // merges tools: into
                                                                  // mounts: at fixed
                                                                  // PATH-visible target,
                                                                  // errors on collision

// manager.go
type Manager struct { /* store *state.Store; isolator Isolator; proxy *proxy.Server;
                          pubsub *pubsub.Client */ }
func NewManager(store *state.Store, iso Isolator, px *proxy.Server, ps *pubsub.Client) *Manager
func (m *Manager) Run(profile *config.Profile, name, namespace string) (*state.Sandbox, error)
func (m *Manager) Update(sel Selector, delta ConfigDelta) ([]UpdateResult, error) // atomic, DESIGN §11
func (m *Manager) Reload(namespace, name string) error
func (m *Manager) Restart(namespace, name string) error
func (m *Manager) Stop(namespace, name string) error
func (m *Manager) Attach(namespace, name string) (*os.File, func(), error)  // pty, detach func

// restart.go
func (m *Manager) watch(sb *state.Sandbox, h Handle)  // goroutine: Wait()s on the handle,
                                                        // applies restart_policy on exit
func backoffDelay(attempt int) time.Duration

// pty.go
type attachRegistry struct { /* mu sync.Mutex; attached map[string]time.Time */ }
func (r *attachRegistry) TryAttach(key string) (already bool, since time.Time)
func (r *attachRegistry) Detach(key string)
const DetachSequence = "\x10\x11"   // Ctrl-P Ctrl-Q
```

### `internal/cli`

One file per command group (`daemon.go`, `profile.go`, `run.go`,
`sandbox.go`, `logs.go`, `status.go`, `broker.go`), each registering its
`cobra.Command`s against the root command in `root.go`. `render.go` holds
the single `RenderTable(v any, cols []string)` / `RenderJSON(v any)` pair
every list/show command calls, so table vs. `--json` is one decision point,
not duplicated per command.

## 6. `cmd/*` Entrypoints

- **`cmd/murod/main.go`**: load `daemon.yaml` → open/create `state.json`
  (`state.NewStore` + `Load` + `Reconcile`) → construct `BwrapIsolator`
  (fail fast per DESIGN §8 host-requirement checks) → construct
  `proxy.Server` and start it on loopback → construct `pubsub.Client` and
  connect (with LWT) → construct `sandbox.Manager` wiring all of the above
  → construct `control.Server` and `ListenAndServe` on `control.sock` →
  block on OS signals (`SIGTERM`/`SIGINT`) for clean shutdown (stop
  listening, do **not** stop running sandboxes — daemon restart shouldn't
  kill agents, only `muro sandbox stop` should).
- **`cmd/muro/main.go`**: `internal/cli.Execute()` — the entire binary is
  that one call; all logic lives in `internal/cli` so it's testable without
  an `os.Exit`-driving `main`.
- **`cmd/muro-broker/main.go`**: load a minimal broker-only config (listen
  address/port, optional MQTT auth), construct a `mochi-mqtt/server`
  instance, add a TCP listener, `Serve()`, block on signals.

## 7. Control API Protocol (request types, DESIGN.md §7/§9)

Every `muro` subcommand except profile management (reads/writes JSON files
directly, no daemon round-trip — DESIGN §9) and `daemon start` (§13 below)
maps to exactly one `Request.Type`:

| `Request.Type` | Payload | Response payload |
|---|---|---|
| `status` | `{namespace?}` | `{sandboxes: []Sandbox}` |
| `sandbox.show` | `{namespace, name}` | `Sandbox` |
| `sandbox.run` | `{profile, name, namespace, agent?}` | `Sandbox` |
| `sandbox.update` | `{selector: {name?, profile?, all?}, namespace?, mounts?, allowURLs?, denyURLs?}` | `{results: []UpdateResult}` |
| `sandbox.reload` | `{namespace, name}` | `{applied: bool}` |
| `sandbox.restart` | `{namespace, name}` | `{ok: bool}` |
| `sandbox.stop` | `{namespace, name}` | `{ok: bool}` |
| `sandbox.attach` | `{namespace, name}` | *(stream upgrade, §5 `control/stream.go`)* |
| `logs` | `{namespace, name, follow: bool}` | *(stream)* |
| `broker.status` | `{}` | `{connected: bool, address: string, lastError?: string}` |
| `daemon.shutdown` | `{}` | `{ok: bool}` — used internally by `muro daemon stop` |

## 10. Testing Strategy

- **Unit tests, per package, no OS dependency**: `config`, `state`,
  `proxy/allowlist.go`, `proxy/sni.go` (test against a raw hand-built
  `ClientHello` byte sequence, not a live TLS handshake), `pubsub/topics.go`,
  `control/protocol.go`, `internal/cli` (against a fake `control.Client`).
- **`sandbox.Manager` unit tests**: run entirely against a `FakeIsolator`
  (in-memory, no real process) implementing the `Isolator` interface — covers
  `Run`/`Update`/`Reload`/`Restart`/`Stop` state transitions, the atomic
  bulk-update validate-then-apply logic (DESIGN §11), and `restart_policy`
  backoff timing, all without touching `bwrap`.
- **Integration tests (`test/integration/`, build-tagged, skipped if `bwrap`
  is absent)**: real `BwrapIsolator` launching an actual sandboxed process
  (e.g. `/bin/true` or a tiny test binary), asserting the mount view and
  denied-network behavior are what the profile says — this is the only tier
  that needs the host requirements from DESIGN.md §8.
- **`muro-broker`/`pubsub` integration**: spin up `muro-broker` on a random
  port in a test harness, connect two `pubsub.Client`s against it, and
  exercise the claim/LWT collision logic (DESIGN §13) for real — this is
  the one piece of §13's design that's hard to trust from unit tests alone,
  since it depends on real MQTT retained-message/LWT semantics.
- No end-to-end test drives a real Claude Code CLI session — attach/pty
  behavior is verified with a small test program that echoes stdin so the
  test can assert raw-mode passthrough and the `Ctrl-P Ctrl-Q` detach
  sequence without needing network access or an API key.

## 12. Milestones / Definition of Done for v1

1. **M1 — Config & state round-trip**: `internal/config` + `internal/state`
   fully unit-tested; a hand-written `daemon.yaml` and profile JSON load,
   validate, and a `state.json` snapshot survives a save/reload cycle.
2. **M2 — Manager against a fake isolator**: `sandbox.Manager` passes all
   its unit tests (run/update/reload/restart/stop, atomic bulk update,
   restart-policy backoff) using `FakeIsolator` — proves the orchestration
   logic independent of real sandboxing.
3. **M3 — Real bwrap isolation**: `test/integration` passes on a real Linux
   host meeting DESIGN §8's requirements — a launched sandbox actually only
   sees its configured mounts and only its configured tools are executable.
4. **M4 — Proxy enforcement**: a sandboxed process can reach an allowed
   host and is blocked from a non-allowed one, for both plain HTTP (full
   URL) and HTTPS (SNI-only) — proves DESIGN §6.2/§14's hostname-filtering
   decision is actually enforced, not just documented.
5. **M5 — Control API + CLI, full workflow**: the exact walkthrough traced
   earlier in this design process — `muro daemon start` → `muro profile
   create` → `muro run` → `muro status` → `muro sandbox attach` (a real
   Claude Code CLI session, confirming pty passthrough and permission
   prompts work) → `muro sandbox stop` — works end to end on a real
   machine.
6. **M6 — Pub/sub + cross-daemon claims**: two `murod` instances (can be
   two processes on one dev machine pointed at the same `muro-broker`) can
   address each other by `namespace/name`, and starting the same name
   twice is rejected with the claim-collision error (DESIGN §13).
7. **M7 — Packaging**: `make install` on a clean VM, `systemctl enable --now
   murod muro-broker`, and the M5 workflow works with no manual setup
   beyond `bwrap` being installed.

v1 is "done" when M1–M7 all pass on a real Linux machine — not before.

## 13. Implementation-Level Notes Not Yet in DESIGN.md

- **`muro daemon start` is not a control-API call.** DESIGN.md §7 states
  "every `muro` subcommand maps to exactly one control API request type,"
  but that can't literally be true for `daemon start`: if `murod` isn't
  running, there's no socket to call. In practice: `muro daemon start`
  execs `systemctl start murod` (or, if no systemd unit is installed,
  forks `murod` directly as a detached background process) and then polls
  `control.sock` until it's reachable or a timeout is hit. `muro daemon
  stop` *does* go through the control API (`daemon.shutdown`, §7) when the
  socket is reachable, falling back to `systemctl stop murod` only if it
  isn't. `muro daemon status` is a pure socket-reachability check, reported
  as "not running" rather than an error when the socket is absent — this
  is the one deliberate exception to §7's rule, not an oversight.
- **Profile validation happens twice by design** (client-side in `muro
  profile create/edit`, daemon-side before every `run`/`reload`/`restart`)
  per DESIGN §10 — implementers should *not* dedupe this into a single
  check by having the CLI call the daemon for validation, since profile
  JSON files can be hand-edited and the daemon-side check is the one that
  actually matters for security; the client-side check exists purely for
  fast feedback while authoring.
